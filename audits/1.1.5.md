## 项目定位

`vanilla-signal-query` 是围绕 `vanilla-signal` 的请求状态管理工具，面向浏览器端业务页面，提供：

- reactive query state
- queryKey 缓存身份
- staleTime 与缓存 ttl
- 请求去重
- retry / retryDelay
- timeout / abort
- prefetch
- invalidate / remove / clear
- local mutate
- 可插拔数据缓存适配器

它不包裹具体 HTTP 客户端实现。`queryFn` 是请求执行边界：用户可以在其中使用浏览器 `fetch`，也可以使用任意独立请求工具。`vanilla-signal-query` 不应该强制用户选择某个 HTTP 工具，也不需要在自身文档中展开描述其它请求工具的职责和用法。

## 1.1.6 源码优化建议

### 1. 复用 vanilla-signal 的公开类型

`vanilla-signal@1.1.14` 已导出更精确的类型，例如 `Accessor`、`MaybeAccessor`、`Computation` 等。当前 `src/core/types.ts` 自己定义的：

```ts
export type Accessor<T> = T | (() => T);
```

语义更接近 `MaybeAccessor<T>`，不是 `vanilla-signal` 中真正的 `Accessor<T>`。继续使用自定义 `Accessor` 名称容易让用户和维护者误解。

建议：

- 从 `vanilla-signal` 复用 `MaybeAccessor`。
- `queryKey`、`enabled`、`initialData` 等 options 使用 `MaybeAccessor<T>`。
- `createEffect` 返回值按 `Computation` 使用，内部不再依赖 `effect?.dispose?.()` 这种宽松写法。

### 2. 收紧 Query 泛型

当前主要泛型是 `Query<TData>`，但 `queryKey`、`queryFn` 原始返回值、`select` 后数据、错误类型没有分开建模，导致公共类型里仍有较多 `unknown`、`any` 和使用侧断言。

建议 1.1.6 设计方向：

```ts
type QueryOptions<
  TData = unknown,
  TQueryFnData = TData,
  TQueryKey extends QueryKey = QueryKey,
  TError = unknown,
> = {
  queryKey?: MaybeAccessor<TQueryKey>;
  queryFn?: QueryFn<TQueryFnData, TQueryKey>;
  select?: (data: TQueryFnData) => TData;
  onError?: (
    error: TError,
    context: QueryCallbackContext<TData, TQueryKey>
  ) => void;
};
```

收益：

- `queryFn` 中的 `queryKey` 可以具备精确 tuple 类型。
- `select` 可以表达“请求返回数据”和“最终 query 数据”的差异。
- `state.error`、`onError`、`retry`、`shouldRetry` 可以逐步从 `any` 收紧为 `unknown` 或泛型错误类型。

### 3. 使用 batch 合并 state 写入

`beginFetch`、`applySuccess`、`applyError`、`resetForNewKey`、`setIdleState` 都会连续写多个 `createDeepStore` 字段。`vanilla-signal@1.1.14` 提供 `batch`，适合把一次 query 状态变化作为一个响应式批次。

建议：

- 从 `vanilla-signal` 引入 `batch`。
- 包裹状态批量写入，减少浏览器端重复调度。
- 保持当前公开 state 字段和语义不变。

### 4. 支持 owner cleanup

当前 `createQuery` 返回后要求用户手动 `destroy()`。这对普通函数调用是合理的，但在 `vanilla-signal` owner/root 生命周期中创建 query 时，可以自动注册 cleanup。

建议：

- 在 `createQuery` 内部检测当前 owner。
- 如果存在 owner，则注册 `onCleanup(query.destroy)`。
- 保留手动 `destroy()`，不改变现有 API。

### 5. 减少公共类型里的 any

当前值得优先收紧的位置：

- `QueryState.error`
- `QueryCacheOptions.options`
- `retry` / `retryDelay` / `shouldRetry`
- `select`
- `normalizeResult`

建议：

- `error` 默认使用 `unknown` 或泛型 `TError`。
- `select` 输入使用 `TQueryFnData`。
- `normalize` 建模为明确的 `NormalizeFn<TQueryFnData>`。
- 缓存 options 拆成 adapter-specific 类型：
  - `MemoryCacheOptions`
  - `CookieCacheOptions`
  - `LocalStorageCacheOptions`
  - `IndexedDBCacheOptions`
- 导出用户会接触到的缓存错误上下文类型，例如 `CacheErrorContext`、`CacheOperation`。

### 6. QueryClientEvent 改为判别联合

当前 `QueryClientEvent` 是宽对象：`type` 是联合字符串，但 `key`、`data`、`error`、`state` 都是 optional。这样使用侧无法通过 `event.type` 获得精确字段提示。

建议：

- 改成判别联合。
- `cache-error` 事件类型进入公开类型和用户文档。
- 明确 persistent cache 写入失败不会改变请求成功结果，但会通过 `cache-error` 暴露。

## 缓存与测试建议

### 1. 持久化适配器 hydrate 行为文档化

`StorageQueryCacheAdapter` 会维护 memory shadow，并异步 hydrate persistent storage。`getAsync` 会等待 hydrate；同步 `getQueryEntry` 只能读取当前已经 hydrate 到 memory shadow 的视图。

建议：

- 在 `docs/query*.md` 的缓存章节说明这个读取差异。
- 描述当前能力，不写历史迁移或移除说明。

### 2. 补充适配器测试

当前单测覆盖了 memory LRU、localStorage、TTL、client cache 继承、`cache-error`。cookie 和 indexedDB 适配器还缺少直接回归用例。

建议：

- `tests/` 中补 cookie adapter 的 options 传递和 ttl 行为。
- indexedDB 若不适合 Node 单元测试，可放入 `demo/` 做手动验证，或用 fake driver 做单元测试。
- 保持 `tests/` 只放单元测试，不再放 HTML 演示页。

## vanilla-request 是否合并

结论：不建议把 `vanilla-request` 合并进 `vanilla-signal`，也不建议合并进 `vanilla-signal-query`。它适合作为独立请求工具存在。

理由：

- `vanilla-signal` 是响应式基础运行时，不应该包含 HTTP 请求能力。
- `vanilla-signal-query` 是 query 管理器，不应该绑定具体 HTTP 客户端。
- HTTP 工具选择属于用户应用层，`queryFn` 已经提供足够的接入边界。

对 `vanilla-signal-query` 的影响：

- 不把 `vanilla-request` 作为依赖。
- 不在 `vanilla-signal-query` 文档中展开介绍 `vanilla-request` 的职责或用法。
- 如果未来需要生态示例，可以放在独立 cookbook 或 demo 中，而不是写进核心 API 文档。
